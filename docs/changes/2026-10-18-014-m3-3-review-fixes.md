## 实现与技术取舍

### 管道写入与监督独立

Python 监督线程只向队列提交对象。专用写线程负责 JSON 序列化、串行 write / flush 和 stdin.close，沿用现有专用 stdout 读线程。这样无须改成新的异步调度器，也不依赖 Windows 不支持的一般管道 select 用法。特别将 stdin 的关闭留在写线程，避免监督线程争用被阻塞写入持有的 TextIO 锁。

timeout / cancel 仍由监督主循环及时记录，控制帧也走同一写入队列，不能与半条工具响应交错。干预后尚未写入的工具响应跳过，已完成的环境操作不回滚。若适配器完全不读管道，控制帧可能无法送达，但监督器仍在原清理期限后尝试终止自有进程树，随后等待读写线程退出。正常路径新增 supervisor.stdinWriterStopped 清理事实；写线程不能结束会记录协议 / 清理错误。

写入异常回传监督器并请求 shutdown，普通运行错误不能变成任务通过。若之前已记录 timeout / cancel，后续 BrokenPipeError 等仍可保留在诊断中，但不会覆盖干预事实。没有改变准备 / 任务 / 清理各自的期限定义，也没有将任务预算宣称为总退出硬上限。

### 发现断言检查结果事实

版本 2 的工具断言允许 `arguments: {}`，表示不限制参数值；沿用现有逐键比较规则，无须新增另一套路径归一化或候选路径列表。非空对象仍精确比较声明参数，版本 1 仍拒绝空对象。工具名称、实际参数为合法对象、callId / toolCallId 关联、结果在最终答案之前、isError 和 textContains 均保留原检查。

stale-path 只对 eval_list 发现步骤使用空 arguments，并要求其成功结果包含 docs/current.md。从 `.` 或 `docs` 发现目标都可通过；读 README、旧路径失败、读当前文件及最终答案仍按原约束检查，没有删除发现步骤。兼容扩展继续使用用例版本 2，证据 / 结果和录制协议均未变化。

## 风险与后续

写入已开始时仍不能把控制帧插入半条 JSONL；依赖监督器原有清理期限和操作系统权限回收失去响应的进程。权限拒绝不能宣称清理完成。写线程与原读线程各有有限退出等待，尚无 token / 步骤预算或任意外部进程树保证。协议队列用于当前受控单会话工具桥接，没有新增并发批次或流式分块。

空 arguments 是显式宽匹配，应该配合工具名、结果及其他必需行为约束使用；它不证明未声明的参数和负向行为。旧运行复验继续使用原 case 快照，不能用更新后的公共用例替代历史约束。

## 面试讨论点

管道背压为何会使“负责执行超时的循环”本身失去响应；为何 write 与 close 都要交给写线程；无法正常送达取消帧时如何保留取消事实并回收资源。任务评测应校验发现目标的证据，避免把特定搜索目录误当作唯一正确行为，同时维持关联与时序检查。
