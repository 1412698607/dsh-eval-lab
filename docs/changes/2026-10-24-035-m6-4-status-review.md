## 审查结果

发现两项 P2，当前只记录，未修改实现或测试：

1. **启动后的证据写入失败没有回收已启动子进程。** [web-lifecycle-live.js](../../scripts/web-lifecycle-live.js) 的 runWeb 先创建原生 ConPTY 子进程，再以 wx 创建 terminal.log；该创建发生在注册 onExit 之前。若 terminal.log 已存在（例如误用旧场景目录），或该文件无法写入，catch 只设置错误，finally 保存报告，既不停止子进程，也不等待实际退出。使用安装好的 node-pty 和一个有 10 秒自退出上限的专用 Node fixture 复现，不启动 Harness / Web / 模型：预置 terminal.log 后 runWeb 返回 1，报告 closed=false，实际 PID 36616 仍存活，原 terminal.log 未变。复现程序随后按精确自有 PID 强停，复查已退出。建议在启动前检查输出条件，并确保启动成功后的任意错误均进入统一回收和退出观测；仅提前检查不能覆盖启动后发生的 I/O 错误。
2. **普通退出的操作和卸载时间未关联到原生生命周期。** [verify_web_live.py](../../scripts/verify_web_live.py) 对普通退出只要求 operation.kind / requestedSignal 正确，未要求 turn/end ≤ operation.at ≤ process/SIGINT；observer/disposed 也只检查存在，未核对与退出事件的先后。复制已有正常成功场景的 case / setup / 清单 / 观察和 traces，分别只把 operation.at 改到 startedAt 后 1 ms（早于页面提交），或把卸载时间提前到首个模型 chunk 并保持观察按时间排序；两份副本经独立 Python CLI 与 fresh Node inspect 均返回 0、liveWebVerified=true、outcome=passed。原始样本及日志不改。这不符合普通退出发生于任务完成后的验收约束；建议将操作、SIGINT 和卸载与对应任务结束关联，并添加正反时间边界回归。

录制器、inspect、通用评测算法和 M2.3 控制器均未在审查范围内发现需要本轮改动的问题；本结论不表示已覆盖所有外部故障。033 / 034 原样本的历史结果保留，这两项反例说明现有回归还缺失败路径和时间关联检查，下一批应先修复再扩大验收。
