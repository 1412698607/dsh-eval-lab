开发日期：2026 年 10 月 7 日。记录整理日期：2026 年 10 月 11 日。代码版本：`0.1.0`。对应已有提交：`8c1b53a`，标题“第一版”。这是一份基于当前代码和已有开发过程补录的历史说明；下面的最新验证日期单独记录。

## 目标与背景

Agent 回归评测需要保留实际执行行为，才能检查工具调用和任务结果。第一批实现聚焦可接入 Harness 的实时记录层，建立事件观察、持久化输出及验证基础。

开发开始时，Windows 工具曾因沙箱初始化失败无法读写。已有错误日志显示运行时文件发生共享冲突，目录切换未立即解决。10 月 7 日后续读写恢复后开始创建代码；最终恢复的具体因素没有独立定位，不把某项配置调整记作已证实根因修复。

## 核心逻辑

宿主在 `apply()` 中创建记录器。每次初始化创建新的运行目录和 `run.json`。新增事件经 `record()` 立即序列化，随后接入该会话的 Promise 链，异步追加至 JSONL 文件。

会话 ID 通过 SHA-256 变为安全文件名，原始 ID 和原始事件保留在每条记录中。相同会话按观察顺序写入，不同会话维护独立状态。`session/flush` 等待选中队列，`dispose` 停止接收并等待全部队列。

首次记录失败保存在会话内存状态中，错误回调报告一次，后续该会话停止录制。检查点抛出 `AggregateError`，其他会话仍可独立写入。

## 实现过程中的问题

- Node.js 默认测试隔离尝试创建测试子进程时遇到 `spawn EPERM`。测试脚本改为 `--test-isolation=none`，在当前环境下运行成功；这是测试运行方式调整，不是插件业务修复。
- 真实组件验证最初没有正确等待 Cordis 服务和插件启动，未获取到预期事件监听。验证脚本改为顺序 `await ctx.plugin(...)`，确认插件 ACTIVE 后再创建会话，接入检查通过。

## 设计取舍

采用纯 JavaScript 避免首版构建步骤；采用 JSONL 逐条追加并保持存储简单；采用会话独立 Promise 链保证观察顺序。相应代价是当前缺少静态类型、队列背压、索引和持久化完整性协议。架构细节见 [架构说明](../architecture.md)。

## 限制与后续

当前是新增事件记录器，没有完整历史补齐、真实模型任务联调、断言引擎或 A/B 配置评测。写入错误只保存在内存，没有持久化完成标记。队列容量、轮转、崩溃恢复和性能基准尚未实现。

后续先完成实际 Harness profile 中的真实任务联调，再定义测试用例和状态化工具环境，逐步增加结果断言与配置比较。

## 面试讨论点

可解释原生插件的生命周期、Promise 链如何保持观察顺序、入队前序列化的原因、写入失败如何影响检查点，以及为何组件接入检查不能代表真实 Agent 评测完成。当前没有性能改善或模型成功率数字可用于成果表述。
