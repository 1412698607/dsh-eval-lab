## 问题与目标

既有八类资源场景记录了内存、写入次数和完整性，但缺少CPU时间、事件循环延迟和持续输入检查。本批先完善测量、冻结来源并取得基线，再根据实际热点做小范围优化；同负载前后必须保持计数、正文、状态和inspect结论。全部使用固定合成输入与真实进程 / 文件，无模型调用。

## 测量先于优化

先保存cf2cccf的Git源码导出，再冻结未改动工作区的7份运行源码 / package文件；两者在仅归一CRLF / LF后逐文件内容一致，实际运行副本保留原字节。测量脚本和helper另行冻结。候选仅session-status.js发生变化；两侧一直使用同一冻结inspect及其全部依赖，避免将验证器变化混入结论。

正式基线为9场景×3次=27个独立Node进程。旧八场景的输入和预期通过 / 失败条件不变；新sustained为500轮、4会话、每轮每会话4条4KiB正文，共8000事件，计划周期40ms，每轮flush，约20秒。固定事件总数和节奏，落后时保留实际迟到量，不追加事件补吞吐。

CPU记录process.cpuUsage的user / system微秒，六个互斥阶段及总窗口；flush / round CPU是producer子集，不再相加。ELU不是CPU利用率。ELD以10ms采样，先预热、reset并有界等待首样本，再开始负载；CPU / ELU在最终GC后结束，ELD额外保留尾部观察。内存采样、rounds和延迟数组也占内存，不能从曲线上涨直接认定录制器泄漏。具体协议与官方API依据见[测量方法](../recorder-profiling.md)。

基线600会话分批场景的墙钟中位数1925.654ms，其中flush累计1591.763ms，入队仅2.657ms；状态文件写入3300次、清单写入8次。它支持优先诊断状态持久化路径，不能把并发I/O累计时间当墙钟相加。独立诊断包装真实unlink，发现成功替换后仍有3307次调用，全部返回ENOENT；诊断的额外计时开销不纳入正式性能样本。

## 优化与安全边界

writeStatus增加一个成功标志，只在await rename成功返回后设置；finally仅在未成功替换时清理临时文件。正常成功时临时名称已被rename移走，不必再次发起必然失败的删除。独立诊断复测为0次unlink，文件与inspect保持有效。

没有跳过flush检查点、减少状态写入或改变成员登记屏障。无新增事件时的flush仍能发现状态路径被目录替换等错误。瞬时重命名失败仍复用同一份临时字节，失败耗尽后仍清理，部分写入失败和清理自身失败仍拒绝。更改不提供fsync、断电保证或完整会话恢复。

## 同负载对照结果

首轮为27个基线进程后接27个候选进程。对照器实际重读源码、measurement、录制与状态文件，核对19563份来源文件并在结束前再次核对摘要；27对全部保持接纳 / 拒绝 / 写入计数、错误、close结果、规范化文件内容和完整inspect结构。原始文件因runId与生成时间不同而不逐字节相同，未声称原始摘要完全相同。

首轮持续CPU出现上涨，因此追加预先明确的AB / BA / AB三轮交错确认，仅重复600会话分批与sustained两场景，共12进程、6对；各轮两侧仍采用同一负载与测量器。六对再次通过内容与inspect核验。以下百分比均是逐对`100×(候选−基线)/基线`的中位数，不是两侧中位数之比；基线为零或数据缺失时为null。

| 场景 / 组别 | 墙钟变化中位数 | flush累计变化中位数 | 进程总CPU变化中位数 |
| --- | --- | --- | --- |
| 600会话分批，首轮3对 | −12.58%（墙钟中位数1925.654→1683.343ms） | −12.80% | −7.27% |
| 600会话分批，交错3对 | −10.12% | −10.47% | −2.36% |
| 持续负载，首轮3对 | −0.005%，固定节奏约20秒 | −6.99% | +20.44% |
| 持续负载，交错3对 | +0.003%，固定节奏约20秒 | −8.06% | +5.25% |

状态密集场景六对墙钟均下降，支持保留该局部优化；不主张所有场景更快。首轮slow-writes墙钟逐对变化中位数为+5.26%，部分短场景CPU也上涨，均保留在[完整公开数据](../benchmarks/2026-11-17-recorder-resources.json)。持续CPU三次分别为4735/4204/6390→5703/5375/5361ms，交错为6766/6250/5938→5438/6641/6250ms，方向混合，不能给出稳定CPU节省结论，也没有足够依据归因到具体系统原因。

每个持续样本均完成500轮，无一轮开始迟到或轮内工作耗时超过40ms；这只是本机该负载观测，不是实时保证。短CPU窗口可出现0或约15/16ms阶梯，不能用几毫秒flush / GC窗口精确归因函数成本。总CPU包含进程所有线程，ELU活跃时间下降不等于总CPU下降。两组结果分别报告，不用复测覆盖首轮或合并为总体胜率。
