# 工程问题复盘

本文整理三个已有记录的问题，说明如何从现象定位到证据、限定修正范围并验证反例。第一个来自受控真实模型任务，第二个来自 Windows CI 与实际短路径复现，第三个来自真实 HTTP 请求的受控工程测试；后两者不是线上事故，也不是新的模型验收。

2026 年 11 月 16 日整理时核对了相关公开修改记录与当前源码。下文测试数量、耗时和运行结果均注明历史记录来源，本次整理没有重新执行模型、测试或浏览器验收。原始运行文件不作为公开文档的链接依赖。

## 案例一：文件操作正确，精确回复仍然失败

### 现象

[109 单文件重命名验收](changes/2026-11-04-109-live-rename-acceptance.md)的一个真实任务完成了预期文件操作，但最后回复 `Done.`，而原冻结用例要求精确 `done`。结果为执行 `completed`、录制 `complete`、评测 `failed`，CLI 退出 1。七条断言中六条通过，唯一失败项是 `answer`。

这里三个状态分别回答执行是否结束、找到的录制是否通过完整性核验、任务是否满足断言，不能相互替代。

### 证据

109 记录核对了 51 条事件、六组工具调用与结果、关联身份和最终状态快照。重命名冲突返回 `TARGET_EXISTS`，随后成功移动到 `archive/final.txt` 并读回正文；最终文件映射为：

```json
{"guard.txt":"keep\n","archive/final.txt":"评测\r\n"}
```

两次独立离线复验仍退出 1，除评价时间外与原结果一致；原任务 16 份顶层及轨迹文件摘要保持。后续对照中，回复证据始终是同一个 `answerSeq=48` 和实际文本 `Done.`。

### 根因

直接原因是回复违反了精确输出契约，不是文件操作失败，也不是评测器误读文本。现有证据不解释模型为什么选择大小写和句号，不能把这一条样本推导成模型的普遍缺陷。

该样本同时暴露了规则表达的两个独立需求：某项是否决定任务总判定，以及该项如何判断匹配。二者需要分别声明，避免用一个总分掩盖操作成功与格式失败的区别。

### 取舍与修正

[110 断言角色](changes/2026-11-04-110-assertion-roles.md)增加 `required` / `diagnostic`，仅控制单项结果是否计入总判定；原文、匹配规则和单项失败继续保存。[111 确认词匹配](changes/2026-11-04-111-confirmation-token.md)另增加 `match: "confirmation_token"`，在单词确认语上接受有限的大小写、配对整词加粗及一个可选英文句号，不接受附加解释或否定句。

| 同一份 109 证据所用规则 | 回复单项 | 任务总判定 | 改变的含义 |
| --- | --- | --- | --- |
| 原必需项、精确 `done` | failed | failed | 原始要求和失败保留 |
| 派生诊断项、精确 `done` | failed | passed | 该失败不计入总判定 |
| 派生必需项、确认词匹配 | passed | passed | 原文符合新的单项匹配规则 |

当前[评测器](../dsh_eval/evaluate.py)分别实现 `_matches_final_text` 与 `assertion_outcome`；[用例校验](../dsh_eval/formats.py)要求至少一条必需断言，并禁止必需工具断言依赖诊断工具断言。录制、身份、配置和执行的全局证据门槛仍然有效。

[112 同轨迹对照](changes/2026-11-04-112-same-trace-assertion-comparison.md)将候选限制为只改断言，重新评测双方并检查来源文件摘要。[对照器](../dsh_eval/assertion_comparison.py)分别记录 `ruleChanged`、`outcomeChanged`、`resultChanged` 和位置变化：`resultChanged` 比较完整断言结果，可能由角色或证据定位变化触发，不等于模型回复改变。

### 验证

110–112 的上述对照全部复用 109 轨迹，没有新增模型任务。112 的三组历史对照均成功完成比较、退出 0；其中原规则两侧依然 `failed`。比较命令成功表示已生成双方结论，不表示任务通过。

[117 新规则矩阵](changes/2026-11-04-117-live-confirmation-matrix.md)才是之后另行执行的四个真实任务：两个用例各两轮，预先冻结确认词必需项与精确回复诊断项。四任务全部通过，32 条必需断言通过；精确回复诊断三通过、一失败，失败样本实际回复为 `**done**`。

[119 实验规则预览](changes/2026-11-09-119-experiment-assertion-preview.md)再次只做离线分析：对 117 四份归档去掉必需回复的确认词匹配，恢复精确 `done`，仅 `timeout-retry / 1` 从通过变为失败。其余三项保持通过，四项均可比较，80 份选定来源文件摘要保持。117 的原结果仍为四项通过。

### 边界

109 的历史失败不被派生规则覆盖，也不与 117 合并分母。确认词匹配不是自然语言语义裁判，不支持任意 Markdown、同义改写或多句解释。对外部系统必须精确解析的协议仍可保留必需精确匹配。文件摘要前后相同不等于原子快照、来源签名或确定性重放；四个新任务也不能证明模型总体稳定性提升。

## 案例二：Windows 8.3 短路径造成测试夹具与解析器不一致

### 现象

归档实现首次 CI 的 Python 步骤失败，而本地此前完整回归通过。[132 短临时路径夹具记录](changes/2026-11-09-132-windows-short-temp-fixture.md)在同一 NTFS 目录的实际 8.3 别名作为 `TMP` / `TEMP` 时，独立复现四失败、两错误。

### 证据

必须保留两个阶段的证据边界：

| 阶段 | 当时已经确认 | 当时不能确认 |
| --- | --- | --- |
| 132：独立短路径复现 | 旧夹具在真实短路径新进程中出现四失败、两错误；修正后普通与实际短路径环境均通过 | 尚未取得原 CI 日志，不能认定它解释原失败的全部原因 |
| [134：取得原作业日志](changes/2026-11-09-134-archive-ci-log-review.md) | 原提交 `5c0cd21` 的 632 项中，四失败、两错误全部位于 `ArchivePathsTests`，逐项对应短 / 长根拼写差异 | 不据一个作业推广所有 Windows 路径问题或跨平台兼容性 |

134 核对的原作业为 run42593809914 / job129081523613 / attempt1。前三个失败直接显示 `runneradmin` 与 `RUNNER~1` 的根拼写差异；其余三个落在同一前缀差异上，表现为 `recognizes` 返回 False、`outside the declared prefixes` 或 `not a listed member or directory`。

### 根因

[ArchivePaths](../dsh_eval/archive_paths.py)构造时对物理 `payload_root` 执行 `resolve()`。旧测试夹具却从未规范化的 `TemporaryDirectory.name` 派生预期路径。在短路径临时根下，同一物理目录分别表示为长根和短根，导致路径相等判断及物理前缀识别不一致。

确定的是测试夹具缺陷；原 CI 的全部失败与它对应，是在 134 取得并核对原日志后才补齐的结论。

### 取舍与修正

只在[路径测试](../test/test_archive_paths.py)的 `setUp` 中先执行 `Path(temporary.name).resolve()`，再构造所有测试路径。生产归档解析器、成员清单、链接检查和原路径禁止回退规则不变。

新增回归用 `GetShortPathNameW` 取得实际 NTFS 别名，将其设为新解释器的 `TMP` / `TEMP`，运行其余路径用例。排除该短路径测试自身以避免递归。这个设计核对真实文件系统行为，同时把修正限制在夹具初始化。

### 验证

132 记录普通环境 13 项通过 / 0.511 秒，实际短路径新进程中的完整路径集 13 项通过 / 0.702 秒，均无跳过。

134 后续从云端实际日志确认：修正提交 `3e09527` 的 633 项 Python / 510.040 秒通过，文档交付提交 `5b0546c` 的 633 项 / 406.839 秒通过；两者均有 154 项 Node 和 45 个 JavaScript 文件语法检查通过。上述数量是对应作业的历史日志结果，不是本次重跑数据。

### 边界

保留首次失败以及 132、133 当时“旧日志未取得”的状态，由 134 追加确认。此修正不代表支持任意外部短路径输入，也不扩大归档路径安全规则。当前回归在非 Windows 或无实际 8.3 别名的卷上可以跳过，不能把这种跳过写为实际短路径通过；历史 132 的环境确实提供别名且无跳过。整个问题与验证均不涉及模型调用。

## 案例三：监听关闭后，HTTP 请求线程仍未退出

### 现象

[139 交付检查复查](changes/2026-11-11-139-baseline-delivery-review.md)发现：交付检查 helper 已回收 `serve_forever` 线程并关闭监听套接字，却可能在两个实际 HTTP 请求线程仍存活时返回。受控测试让 handler 已发送完响应，再停在 `finish` 收尾阶段，稳定暴露了这个时序窗口。

### 证据

[新增回归](../test/test_delivery_check.py)使用真实服务、HTTP 连接和请求线程。它包装实际 handler 的 `finish`：先执行原收尾，再保存当前线程并等待 `Event`；测试等到服务开始关闭后，检查 helper 在放行前不得返回。

该测试分别覆盖正常文档请求与无效文档产生的 HTTP 错误路径。两种路径都实际创建两个请求线程，放行后逐一确认线程已结束。`Event` 只控制真实线程的收尾时点，没有模拟退出结果。

### 根因

[浏览服务](../dsh_eval/browser.py)使用 `ThreadingHTTPServer`，其默认请求线程为守护线程。原交付 helper 的 `server_close()` 不等待这些守护请求线程；主服务线程已结束和套接字已关闭，都不能证明所有请求处理已经结束。仅遍历默认未登记这些守护线程的 `_threads`，还可能得到空集合上的通过结论。

### 取舍与修正

仅在[交付检查的 `_http_check`](../dsh_eval/delivery_check.py)新建服务后设 `server.daemon_threads = False`，让 `server_close()` 等待本次服务创建的请求线程。正常与异常路径共用 `finally`：先停止服务循环，再关闭服务并等待请求线程，最后等待主服务线程。

通用浏览服务的默认行为不变，修正没有扩展成整个浏览器生命周期重构。代码中的主线程 `join(timeout=10)` 不限制此前 `server_close()` 的等待，因此不能宣传清理具有十秒或其他总耗时硬上限。

### 验证

139 记录在测试进程内移除新加的 `daemon_threads` 设置，磁盘源码保持不变：新增回归的正常 / 错误两个子测试均按预期失败，证明测试能发现旧行为提前返回的问题。

修正后，实际链接环境中的九项交付检查 / 28.624 秒全部通过，无跳过，包含正常和错误请求收尾。最终完整回归为 673 项 Python / 420.176 秒、165 项 Node / 7.088 秒和 45 个 JavaScript 文件语法检查通过。首次受沙箱链接权限限制的错误另行保留，不算作最终通过依据。

### 边界

这是受控工程测试发现并修正的线程清理缺陷，没有线上事故或请求永久阻塞的证据。验证限定交付检查自建服务、上述正常 / 错误请求及 Windows 环境；它不证明任意服务、外部工具树或其他平台均能退出。139 的记录还包含另一项前端元数据修正，本文只复盘 HTTP 问题；本案例没有新增模型任务。
