# M2 可靠录制与真实任务联调方案

日期：2026 年 10 月 11 日，Asia/Shanghai；2026 年 10 月 12 日更新。状态：M2.1、M2.2 已实现并验证，当前插件 `0.1.2`；M2.3 仍为方案。依据见 [修改记录 004](../changes/2026-10-11-004-m2-1-output-config.md) 和 [修改记录 006](../changes/2026-10-12-006-m2-2-recording-integrity.md)。

下一阶段目标是形成可检查的真实任务录制闭环：启动带插件的 Harness，执行一个受控任务，保存轨迹，并能从磁盘判断该录制片段是否正常结束、内容是否完整一致。完整回归评测引擎在 M3 开发。

## 访问渠道与核心边界

录制核心复用同一套逻辑。它依赖兼容版本的 `sessions` 服务，接收 `session/event`，并处理检查点和关闭。浏览器、桌面与自动化入口主要影响安装位置、插件组合、启动方式和退出时机。

| 渠道 | 需要适配的部分 | 本阶段定位 |
| --- | --- | --- |
| Web | web profile、服务端启动和正常关闭、页面内任务操作 | 首个人工联调基线；这是暂定入口，不表示用户已确认主要使用方式 |
| 桌面 | 桌面自带运行时、保留 profile 和安装入口 | 核心保持兼容设计，实际桌面版本明确后再验证；不套用任意 npm CLI 管理桌面 profile |
| headless | 单任务进程、退出码、JSON 输出和关闭链路 | 首个可脚本化真实任务验证入口 |
| SDK | profile、JSON-RPC stdio、会话与进程生命周期 | M3 自动化评测候选入口；本阶段先修复输出通道冲突 |

相同事件接口不代表不同 profile 的工具、权限、提示词和任务结果完全相同。验证报告需要记录版本和 profile，不能把某个渠道的成功推定为所有渠道都通过。

原入口的 `console.info()` 使用 stdout，而 SDK 将 stdout 用于 JSON-RPC；headless 的 JSON 模式也需要保持结构化输出。M2.1 已把插件诊断统一写到 stderr，轨迹写到文件，并验证真实组件子进程的输出边界。各 profile 的整体协议和真实任务仍待联调。

## M2.1 输出与配置设计

### 输出通道

`src/index.js` 的启动信息和错误报告统一走 stderr。配置或版本校验失败应有明确错误信息。不能向 SDK、ACP 或 headless 的协议 stdout 插入普通文本。

增加一个真实子进程输出检查：在独立子进程中挂载插件，验证 stdout 没有插件文本，stderr 包含诊断。该用例属于运行时输出边界检查；如果当前沙箱限制创建子进程，应报告未验证并在外部终端复现，不能用同进程 mock 代替通过结果。

### 路径优先级

已实现以下优先级：

1. 显式 `config.outputDir`，继续要求绝对路径。
2. 环境变量 `DSH_EVAL_OUTPUT_DIR`，同样要求绝对路径。
3. 当前用户主目录下的 `.dsh-eval-lab/runs`，使用 Node.js 路径工具生成绝对路径。

默认目录不依赖插件安装位置和宿主当前工作目录。项目演示与测试仍显式指向项目内 `runs/` 或临时目录。移除分发 patch 中绑定开发机盘符的路径；联调时通过本地覆盖配置将日志写到项目的 `runs/`。

优先级选中的值无效时直接报告错误，不静默退回下一项。日志保存位置在 stderr 中明确输出。

### 版本策略

沿用已验证的 DSH 会话组件 `0.2.0-rc.2` 和 Cordis `4.0.4` 作为基线，不隐式升级。真实联调前记录实际宿主版本、profile 和插件版本。M2.1 已修正显式路径未校验版本的问题，并在自动查找时核对两个组件。

实施修正：Cordis 4.0.4 的 FiberState 是 const enum，运行时没有该导出，原定“使用实际导出的状态常量”不可执行。改为在脚本中定义有类型声明来源注释的 `HOST_FIBER_ACTIVE`，仅在组件版本校验通过后使用。插件本身仍使用可选 peer 声明，不额外加载宿主实现。

桌面版与 CLI 的管理能力可能随版本变化。当前官方文档对桌面 profile 的限制与早期缓存 CLI 的行为存在差异，因此安装步骤必须以实际安装版本为准，不假设 npm CLI 可以管理任意桌面安装。

## M2.2 状态和完整性设计

2026 年 10 月 12 日实施说明：以下设计已落地，36 项测试及真实组件封存检查通过。真实子进程验证正常、磁盘错误和未关闭直接退出三种场景。最后一种是受控 `process.exit(0)`，不是操作系统强杀或断电实验。真实组件暴露旧 `ctx.on("dispose")` 未执行关闭的问题，改为 `ctx.effect()` 注册异步清理；历史判断修正见修改记录 006。

### 输出结构

保留当前 JSONL 包装格式和事件内容，新增独立状态文件，避免把录制器内部状态混入 Harness 事件：

```text
runs/<runId>/
  run.json
  <session-hash>.jsonl
  <session-hash>.status.json
```

新状态文件使用独立的 `statusFormatVersion: 1`，记录运行与会话身份、状态、已接收和已写入条数、序号边界、字节数、校验摘要及错误信息。现有 `formatVersion: 1` JSONL 保持可读；没有状态文件的旧日志只能报告为未验证，不能自动升级为完整。

### 状态与含义

| 状态 | 含义 | 离线处理 |
| --- | --- | --- |
| `recording` | 录制片段仍开放，或进程在正常封存前退出 | 可显示诊断和已检查点前缀，不作为完整片段输入 |
| `sealed` | 已停止接收，全部接收事件写完，封存状态文件写入成功 | 仍需复核条数、字节数、序号与 SHA-256 后才接受 |
| `failed` | 接收、写入、容量或状态更新失败 | 报告失败，拒绝完整片段资格 |
| 状态缺失或不可解析 | 旧格式、元信息损坏或状态写入失败 | 报告未验证或损坏，禁止仅凭 JSONL 文件存在判成功 |

`sealed` 只描述本插件观察到的录制片段，不代表整个历史完整、任务成功或断电可靠。正常关闭时仍可能是一个任务失败的有效片段。未来的 `passed`、`failed`、`runtime_error` 属于评测层，不能与录制状态混用。

M2.1 已观察到 session/flush 能传播录制错误；M2.2 新增的真实清理路径确认 Cordis 4.0.4 会捕获清理错误，所以不能用 fiber.dispose 完成代替 sealed 状态检查。旧 dispose 监听未执行关闭的历史判断修正见修改记录 006。

### 写入与封存顺序

1. 首条会话数据写入前，在该会话队列中初始化 `recording` 状态；初始化失败则不继续正常录制。
2. `record()` 保持接收时序列化，在会话队列中追加数据；实际写入成功后更新写入计数、边界和字节摘要。
3. `flush()` 捕获选定队列检查点，写入该检查点的计数、字节长度和摘要。会话保持 `recording`，不能因为一次 flush 就把后续仍可追加的文件称为已封存。
4. `close()` 先停止接收新事件，等待所有队列，再为未失败会话保存 `sealed` 状态及最终摘要。主机应先让 Agent 停止产生最终事件，再卸载录制器；该顺序必须在真实关闭链路验证。
5. 状态通过同目录临时文件与 rename 更新，失败时保持保守状态并报告。Windows 上的替换与文件占用行为需要实际测试，不预先承诺所有文件系统上的原子持久性。

写入错误可能使 `failed` 状态本身也无法保存，因此离线工具必须把剩余的 `recording`、缺失状态和不匹配摘要视为不可接受。`session/disposed` 是观察事件，不能把它当成宿主一定等待的异步持久化屏障。

### 序号和捕获范围

保留 `captureScope: live-events-only`。检查日志中的原始序号为合法整数并严格递增，显示起止序号及缺口；不进行排序、补造事件或自动去重。新会话联调用来观察完整任务区间，已有会话、恢复和 fork 的前缀覆盖保持明确的未知边界。

### 容量保护

增加记录器级 `maxPendingBytes`，默认 16 MiB，并允许配置调整。按 UTF-8 编码后的待写入字节数记账，写入完成或任务被跳过时释放。超过上限时停止受影响会话的录制并报告容量错误，不能静默丢事件继续宣称完整。

这只约束排队文本的字节数，不是 Node.js 总内存上限。序列化临时对象、会话状态、单事件体积与操作系统缓存另计；本批次不宣称解决全部内存与长期运行问题。日志轮转和会话状态淘汰后续按使用量单独开发。

### 离线检查命令

已增加命令，参数明确指定运行目录，避免默认选择“最新文件”造成误读：

```powershell
npm.cmd run inspect -- --run 'D:\codexWorkspace\dsh-eval-lab\runs\<runId>'
```

读取时逐行解析并对原始文件字节计算摘要，核对运行和会话身份、记录条数、字节数及序号。空文件、残缺末行、非法 JSON、损坏元信息和摘要不匹配均给出原因。未知事件类型可以展示，检查器不承担 Harness 完整历史重建。

退出码为：`0` 表示找到的录制片段均已封存且结构校验通过；`1` 表示明确失败或损坏；`2` 表示仍开放、缺少状态或无法确认。该退出码不表示 Agent 任务通过。检查应针对停止写入后的目录或稳定副本；SHA-256 不提供签名验证，也没有运行级清单来检测整对会话文件被删除。

## M2.3 真实任务联调

### 环境与任务

采用项目下独立的临时或测试工作目录，不让任务修改插件源码。提供一个 README fixture，包含明确的 `projectName` 字段；任务要求读取它并返回字段值。通过实际宿主使用的文件工具执行，工具名称从真实事件确认，不把演示中的 `read_file` 硬编码为唯一正确名称。

首次 Web 联调确认安装、记录和正常退出。首次脚本化验证优先使用 headless，一次任务对应新会话与可控进程生命周期；后续多轮评测再评估 SDK。沿用现有模型配置，执行前确认路由可用，不把凭据写进方案、日志示例或仓库。

### 验证场景

| 场景 | 预期检查 |
| --- | --- |
| 读取 README 并回答字段 | 可关联用户消息、实际工具调用、返回内容、助手消息和轮次结束；正常退出后片段通过 inspect |
| 请求读取不存在的文件并报告结果 | 能观察工具错误和后续响应；工具失败不自动等于整个 Agent 任务失败 |
| 任务取消 | 记录实际取消与结束事实；可在控制组件中稳定测试，并单独说明真实模型人工取消是否验证 |
| 录制进程被强制停止 | 状态保持开放或不可确认，inspect 不得返回完整成功；使用独立测试子进程执行，不终止用户正在使用的宿主 |
| 日志被截断或内容修改 | 摘要或结构校验失败，不作为完整片段 |

一条真实任务不能证明 Agent 在所有任务上的可靠性。没有足够重复样本前，不报告通过率提升或费用改善。

## 验收与测试

- 现有 6 项功能测试和真实会话组件接入检查继续通过。
- flush 之后继续追加、追加与检查点交错、正常关闭、重复关闭和错误后关闭的状态一致。
- 队列超限、状态写入失败和日志损坏不能产生可接受的完整状态。
- 旧日志可以诊断但不能被误判成新格式的已封存日志。
- 真实宿主输出不被插件文本污染，安装版本和运行 profile 可核对。
- 至少完成一个真实模型任务的完整闭环，并将使用渠道、任务输入、结果和录制检查分别记录。

真实模型、子进程或桌面验证如果受环境限制，单独保留为未完成验收项，不以模拟测试替代。

## 后续 M3 方向

M2 后定义 `caseRunId`，使每次评测与插件启动 `runId` 分开。每个用例使用新的 Agent 会话，固定初始状态和预算。实现状态化虚拟文件系统和确定性断言，区分任务结果、运行错误和录制错误，再考虑重复运行与配置比较。

首批候选场景为“README 路径过时”和“工具失败后恢复”。工具模拟根据参数及当前环境状态响应，避免按调用序号机械回放历史结果。
